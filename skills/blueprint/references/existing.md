# Existing projects

Read this when *Where you start* in `SKILL.md` chose Existing or From scratch. Existing uses the first part only; From scratch uses both.

## Reading an existing project

The code shows what the project does. The documents record that, plus the intent behind it, so someone new can find their way around, fix it, and extend it.

1. **Read thoroughly.** Find the entrypoints, how to run and test it, the main flows, the data, and outside services. Run the tests and the safe commands that show behavior, and note the results; never run anything that sends, deploys, deletes, or touches real accounts. Where the README, comments, or tests disagree with the code, the code shows what happens, and the disagreement is a finding. A project with no code to run (documents, prompts, a skill) gets the checks its kind allows instead, such as validating its manifests and measuring sizes; those are its tests.
2. **Point to the code.** Every interface, rule, and data structure in SPEC names the file and function that implement it (e.g., `rules.py` `available_slots()`). Put the commit you read (or the date, outside git) in each document's Mode line.
3. **Built is not the same as intended.** For each finding (a contradiction, a crash, a mismatch with docs or tests), judge from the evidence whether it is a bug or intended: tests, docs, commit messages, and how the rest of the code treats the case. Intended behavior becomes a requirement; a bug becomes a task. When the evidence can't tell and the answer changes what gets built, it is a question for the round if it passes *Asking* in `SKILL.md`, or else an Open question.
4. **Write.** PRD: what it does today, for whom, and what it deliberately doesn't do. SPEC: how it works, marked [Code]; a past decision whose reason no evidence gives goes under Open questions, never an invented reason. TASKS: the work the findings call for, most serious first: bug fixes with a regression test that fails first, doc fixes, missing tests for important rules, and code too unclear to change safely.

## From scratch

The old project is evidence, not a spec. Keep its idea; decide everything else again from zero, its promises to the outside world included, but never break one without a transition.

1. **Read the old project** as in *Reading an existing project* step 1, and record its commit (or the date) in each document's Mode line. Take four things from it:
   - **Core idea**: the problem, the users, and the outcome they get. This is the only part of the old design carried over as given.
   - **Outside contracts**: whatever outside the code depends on it: files or data other programs read or write, stored user data, API endpoints and fields, commands that scripts call, IDs and names shared with other systems. That they exist is a fact; whether to keep them is a design decision like any other. Keep a contract when it serves the core idea. Change or drop it when a clearly better design needs that, recorded in SPEC Decisions as [AI] with the reason and what it costs the people who rely on it. A changed contract gets a transition: stored data is migrated, and where consumers outside the files may exist, the new version still accepts the old form for a while after the switch-over (e.g., the old command name still runs and points to the new one). Ask whether anyone else depends on an output only when its consumers are not in the files and no transition is possible. Live data the old version keeps writing stays where it is: the new version works on a copy until the switch-over, and its branch never commits changes to that data.
   - **Lessons**: bugs, crashes, workarounds, slow or confusing parts. Each becomes a requirement or check the new version must meet, not code to copy. When several share one cause, the cause is the lesson, and the new design removes it.
   - **Why it is being rebuilt**: the person's dissatisfaction with the old version is part of the center. The new design must answer it, not just be newer.
2. **Design from zero.** Write the PRD from the core idea, not from the old feature list. Keep an old feature only when the core idea needs it; list each dropped one under Out of scope with a one-line reason, so nobody re-adds it. Choose the stack and structure as for a new project. Reusing the old ones is fine only when they win on their own merits, recorded in Decisions.
3. **Decide where the new code goes**, in SPEC Decisions. Default: a new branch in the same folder. The documents need no copy, since git leaves ignored files in place across branches, and every session opens where it already does; the old code stays readable at the recorded commit. Outside git, the first task makes the folder a repository and commits the old version first. Use a new folder (in git, a `git worktree`) only when the old version must keep running on this machine while the new one is built, such as a live service or the live data above. Blueprint only records the choice; the first task creates the place.
4. **Plan the TASKS.** The first task creates that place and adds the *Plan* section to the instruction file there. On a branch, it also lists the ignored files the old version left (`git status --ignored`) and removes the build outputs and dependency folders among them, keeping `docs/blueprint/` and the settings the new version still needs, so old files do not pass for new ones. In a new folder, it copies `docs/blueprint/` there, adds the *Plan* section in the new folder (not the old one), and tells the person to continue there. A check that runs the old version uses a temporary worktree at the recorded commit and removes it afterwards. A check that proves each kept contract against the old version (it reads the old version's files correctly, and what it writes keeps the format outside readers expect), and each changed contract's transition (old data migrates, the old form still works), comes as soon as the slice that touches it exists. The check holds the new version to the contract, not to the old version's bugs: where the old output is wrong, the requirement decides. The last task is 👤: switching over from the old version, since replacing a working system is the person's call; it includes a check for each assumption about an outside contract (e.g., the finance spreadsheet still imports the file), telling the users of each changed contract what changes, and a date to remove each old form. SPEC points to the old code at the recorded commit wherever a check compares against it, so the coding agent and the fresh reader in *4. Review* can read it there; give that fresh reader the commit path too. The report names every changed contract first among the [AI] decisions.
